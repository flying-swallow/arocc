# Aro C3 migration: reference and regression inventory

This file records the Zig reference that the C3 port is measured against, what
was and was not executed, and how to rebuild the reference later. The
machine-readable copy is `test/migration/baseline.json`. It is generated by
`test/migration/inventory.py` and must not be edited by hand.

## Reference status: not executed (compiler unavailable)

- `build.zig.zon` requires **Zig 0.18.0-dev.828+9da287565** (`minimum_zig_version`).
- None of the Zig executables here can build this repo. The pinned dev build can't be
  downloaded because ziglang.org is blocked. An older Zig (for example
  0.17.0-dev.1818) must not be used: its failures are toolchain mismatches,
  not Aro regressions. Do not change Zig sources to suit it.
- As a result, **none** of `zig build`, `zig build test-unit`,
  `zig build test-integration`, `zig build test-record` or `zig build test-fmt`
  has been run. `baseline.json` records
  `"reference_status": {"status": "reference not executed: compiler unavailable", "pass_fail_counts": null}`.
- No pass, fail or skip counts exist for the reference. The numbers below
  are **fixture inventories taken from the source**, not test results. Never
  report a green Zig suite, or differential parity against a Zig binary, until
  there are logs from a real run.
- In the meantime, the Zig source code is the reference. Expected values come
  from the checked-in fixtures (`test/cases`, `test/records`, embedded
  `test` blocks) or from reading the Zig code. Any data derived that way is
  marked as source-derived (see `plan/PARALLEL.md`).

## Regenerating the inventory

```sh
python3 test/migration/inventory.py          # rewrite test/migration/baseline.json
python3 test/migration/inventory.py --check  # exit 1 if the checked-in file is stale
```

The script only reads files, and it applies the same rules as the Zig harnesses:

- `test/runner.zig` `caseFromFile`: the manifest runs from the first `/** manifest:`
  to the **last** `*/`. The first line gives the kind. Then come `key = value`
  lines (`skip`, `args`, `env`) up to the first blank line. Every line after that
  is trailing data.
- `test/record_runner.zig` `parseTargetsFromCode`: the `// MAPPING|DEFINE|target:Compiler|...|END` lines.
- `test` blocks in `src/`, `build/` and `test/` `*.zig`.
- `pub` declarations in `src/aro.zig` and `src/backend.zig`.

The output is sorted, and nothing is read from the host at generation time, so
the counts can be reproduced. `recorded_environment` in the script is a fixed
note of the environment the baseline was taken in.

## Integration fixtures (`test/cases`, 492 top-level `.c` files)

The harness is `test/runner.zig`, run with cwd `test/cases`. Subdirectories
(`ast`, `embed`, `expanded`, `frameworks`, `include`) hold support files and are
not cases. All 492 manifests parse. None has an unknown option, an invalid kind
or an invalid env pair.

| Kind | Count | arocc flags | Checked |
|---|---:|---|---|
| `syntax` | 387 | `-fsyntax-only --verbose-ast` | diagnostics, plus stdout == `ast/<case>.c` if that file exists (34 do) |
| `syntax_ignore_errors` | 7 | `-fsyntax-only --verbose-ast` | `ast/<case>.c` if present; diagnostics ignored |
| `expand_error` | 41 | `-E -P` | diagnostics only |
| `expand` | 52 | `-E -P` | diagnostics, plus stdout == `expanded/<case>.c` (required) |
| `expand_partial` | 4 | `-E -P` | diagnostics, plus stdout **ends with** `expanded/<case>.c` (required) |
| `compare_output` | 1 | none | **unimplemented**: the runner prints `TODO compare output`, counts 1 skip, and never runs arocc |

- Active cases: **491**. Unimplemented `compare_output`: **1** (`hello world`).
- 281 cases pass `args`, and 2 pass `env`.
- 22 cases carry 29 `skip =` lines. A skip does **not** stop a case from running.
  Each skip line is printed and added to the skipped total after the case
  passes. If every case passes, the runner should print
  `491 passed; 30 skipped.` (29 skip lines + 1 compare_output). That is a
  prediction from the source, not an observed result.
- Every `expand` and `expand_partial` case has its `expanded/` golden. There
  are no orphan `ast/` or `expanded/` goldens.
- How diagnostics are checked: the runner keeps the stderr lines that contain
  `error: `, `warning: ` or `note: `, dropping the Darwin `--sysroot` note. It
  matches them in order against the trailing lines by substring, and the two
  counts must be equal.
- Note: `test/README.MD` says `expand_partial` checks that the output "contains"
  the trailing data. The runner's actual behavior (suffix match against
  `expanded/`) is the reference.

The per-case list (kind, args, env, skips, expected diagnostic count, golden
presence) is in `baseline.json` under `integration_cases.cases`.

## Record layout fixtures (`test/records`)

- 88 `*_test.c` files hold 9353 (file, define, target) cases: Clang 5569, Gcc
  3336, Msvc 448. The per-arch and per-OS split is in the JSON.
- The runner counts os `ios`/`macos` with arch `x86`/`arm` as *invalid
  targets* and does not run them. That predicts 344 invalid targets and
  9009 cases to run.
- There are 2 expected failures (`compErr`), both
  `x86_64-x86_64-windows-gnu:Gcc` for tests `0068` and `0082`
  (layout + extra). `global_test_exclude` is empty.
- Prerequisites: a built `arocc` passed as argv[1], cwd at the repo root, and
  the pinned Zig's `std.Target.Query.parse` accepting every target and cpu
  model string. Without that Zig, it's unknown whether strings such as
  `maccatalyst`, `tvos` or `other` parse, so the predicted count is an upper bound.
- Quirk: the "All N tests passed" branch compares `ok_count` to the number of
  *files* (88), not the number of cases. A fully green run therefore prints
  `N passed; 0 skipped (M invalid targets).`

## Parity requirements: experimental backend limitations

These describe how the backend behaves now. The C3 port must match this
behavior. They are not promises to implement the missing codegen.

- Once past `-fsyntax-only`/`-E`, only x86_64 ELF is accepted. Anything else
  is fatal: `unsupported target {arch}-{os}-{abi}, currently only x86-64 elf is supported`.
- `-O0` selects the assembly backend. Every other `-O` level uses AST→IR
  (`CodeGen.genIr`) and then `Ir.render`.
- The assembly backend (`src/assembly_backend/x86_64.zig`) supports x86_64
  only (any other arch panics). It emits **data only**:
  - Function definitions produce `TODO: Codegen functions`.
  - Aggregate, array, struct and union initializers produce `TODO: Codegen multiple inits`.
  - `_Complex` values produce `TODO: Codegen _Complex values`.
  - Integers that are not 8/16/32/64/128 bits produce `TODO: Codegen _BitInt values`.
  - Pointer values produce `TODO: Codegen pointer`.
  - It does emit scalars, f16/f32/f64/f80/f128, strings, `.data`/`.bss`/`.tdata`/`.tbss`/`.comm`,
    `-fdata-sections` naming, `.file` (unless the debug format is strip), and the `.note.GNU-stack` section.
- The IR x86 renderer (`src/backend/Ir/x86/Renderer.zig`) fails every decl
  with `TODO implement lowering functions`. The driver then reports
  `unable to render Ir to machine code: ...`.
- AST→IR (`src/aro/CodeGen.zig`) fails with `TODO ...` on all of these:
  - global asm
  - struct bitfields, unions, blocks, complex, atomic, VLAs, `nullptr_t`
  - case ranges
  - various statements, expressions, casts, lvalues, builtins and initializers
  - static/thread-local compound literals
  - memcpy
  - global variables
- `Object` supports ELF only.

## C3 build (Bazel + c3c), already in the tree

- `MODULE.bazel` declares module `aro` and a `c3c` repository rule
  (`tools/c3c_repo.bzl`). The rule finds the host `c3c` from `$C3C` or
  `PATH` and exposes `@c3c//:c3c` and `@c3c//:stdlib`. It warns if the
  version isn't 0.8.5. This toolchain is local and not hermetic.
- `.bazelversion` pins Bazel 9.1.0. `.bazelrc` points the registry at the
  GitHub-hosted BCR (`bcr.bazel.build` is blocked), disables the lockfile and
  passes `C3C` through `--repo_env`.
- `tools/c3.bzl` defines these rules:
  - `c3_library`: collects sources only.
  - `c3_binary` and `c3_test`: one `c3c compile`/`compile-test` action over all
    transitive sources. They use `-O0` by default and `-O2` under `-c opt`.
- Targets:
  - `//:aro_c3_lib`: `src/c3/aro.c3`.
  - `//:aro_c3`: `app/aro_c3/main.c3`.
  - `//test/c3:build_smoke`: `test/c3/build_smoke.c3`.
- Sources are always listed explicitly in `BUILD.bazel`, never globbed. Only
  the integrator edits the shared `BUILD.bazel` files.

```sh
C3C=/home/user/tools/c3/c3c /home/user/tools/bazel \
  --output_user_root=/home/user/tools/bazel_root test //test/c3:build_smoke      # add -c opt for opt
C3C=/home/user/tools/c3/c3c /home/user/tools/bazel \
  --output_user_root=/home/user/tools/bazel_root build //:aro_c3
```

Tools recorded here: c3c 0.8.5 (`/home/user/tools/c3/c3c`, LLVM 23.1.2) and
Bazel 9.1.0. The c3c 0.8.6 pre-release pinned in plan 02 needs LLVM 19+ to
build from source.

## Rebuilding the Zig reference later

Do this once a Zig `0.18.0-dev.828+9da287565` (or a compatible later build) is
available. Keep its outputs out of the source tree so they can't affect the
C3 build:

```sh
REF=$HOME/aro-zig-ref            # separate output + cache directory
git worktree add "$REF/src" 29b8685bd464be5849e36a83f37bdc070919e39b
cd "$REF/src"
zig version                                   # must print 0.18.0-dev.828+9da287565 (or compatible)
zig build            --cache-dir "$REF/cache" --global-cache-dir "$REF/gcache" --prefix "$REF/out" 2>&1 | tee "$REF/build.log"
zig build test-unit  --cache-dir "$REF/cache" --global-cache-dir "$REF/gcache" --prefix "$REF/out" 2>&1 | tee "$REF/test-unit.log"
zig build test-integration --cache-dir "$REF/cache" --global-cache-dir "$REF/gcache" --prefix "$REF/out" 2>&1 | tee "$REF/test-integration.log"
zig build test-record      --cache-dir "$REF/cache" --global-cache-dir "$REF/gcache" --prefix "$REF/out" 2>&1 | tee "$REF/test-record.log"
```

Keep `$REF/out/bin/arocc` (plus `$REF/out/include`) as the executable for
differential checks. After that, update `reference_status` and the
`recorded_environment` block in `test/migration/inventory.py` with the real Zig
version and the actual totals from the logs (including every failure and its
reason), and regenerate `baseline.json`. Until then, the expected outcomes
above are predictions from the source.
